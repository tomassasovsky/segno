### Residuals

**R1 — transient false notice during a *successful* Session load (low, uncovered).** `monitor_cubit.dart:147-151` emits `restoreFailed: true` whenever an attempt is retired with the session revision unchanged. A session load flips `sessionTransitionActive` synchronously at `source/lib/session/cubit/session_cubit.dart:511`, *before* `applySession` bumps the revision. So if a session is loaded while the launch restore is still between checkpoints, the attempt bails, `whenComplete` sees the old revision, and the persistent error toast is shown on the next frame — cleared only after `projectFromRepository()` (`source/lib/looper/view/looper_page.dart:18-19`). Window ≈ the settle cycles after launch. The three `Session reservation during $stage` cases (`monitor_restore_test.dart:939-966`) only exercise the *canceled* reservation, so this path is untested. This is the deliberate REC‑3 trade (false alarm over lost Retry) and I'd keep the code; the gap is that `docs/code-review/monitor-mute-admission/review.md` "Behavior and ownership" doesn't state it. Add one sentence, or a test for the reservation→apply→projection path.

**R2 — session applied, boot image failed: empty projection with no notice (low).** In the same window, if the session applies and then its boot settings fail (`markSessionBootFailed`, `source/lib/app/fx_chain_persistence.dart:75-78`), the revision has changed so `:147-151` correctly skips the emit, but `_restored` stays `false` because LooperPage projects only on `outcome == loaded`. `MonitorState.inputs` stays empty with no Retry. Also, while `_sessionBootRecovery != null`, `cancelSessionLoad()` is a no‑op (`fx_chain_persistence.dart:68`), so a showing monitor Retry returns `false` every time — truthful but inert, and the message points at the wrong blocker. Both self‑heal when `retryLoadedSession()` succeeds.

**R3 — superseded errors are dropped entirely (informational).** `monitor_cubit.dart:137-141` returns before `addError` when `stillOwned()` is false. Base always reported. Reachable only when close/projection/session wins the race, where the state is no longer authoritative — but there is no log either.

**R4 — failed restore still under‑reports admitted commands (disclosed limit).** `state.inputs` is first emitted at `:198`, after all admissions, so on failure the console shows no configured monitors while `_applyMonitor` (`:903-923`) may already have admitted mode+output — for earlier inputs, and for the refusing input itself when its saved mute is `false` (mode/output are written unconditionally at `:910-912` before the unmute).
