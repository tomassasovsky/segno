# Preexisting / out-of-scope (not introduced by this PR)

1. Reconnect during the Session fence strands the device (`looper_repository.dart:2325-2345`). `_attemptReconnect` short-circuits only on `_applyingSessionRevision`; if a pinned device returns while `_sessionBootStartBlocked` is set, it raw-stops the engine, `startEngine` returns `notReady`, `_lastAttemptSignature` is recorded, and later ticks return early with the same signature even after the fence clears (`_superviseDevice` does not reset it because `_isReconnecting` is already true). Smallest fix: add `|| _sessionBootStartBlocked` to the early return at 2326, or reset `_lastAttemptSignature` in `clearSessionBootStartBlock`. The fence and this supervisor both predate the PR; the PR does not widen the window because apply was already covered by the revision reservation.
2. After a boot failure the engine is stopped and stays stopped after a successful retry; the user must restart it. Existing design, unchanged.
3. The first explicit Play after a recall now goes through `le_launch_defer` (2018-2019, 348): with record-start count-in bars configured, the launch is deferred behind a count-in exactly as a Play from a manually held transport is. This is the "existing held-transport behavior" the boundary accepts, but it is a user-visible change from the old immediate start and belongs in release notes.
