## What the change actually does

Four Dart files plus two docs. The correction has three parts:

1. `LooperRepository.setMonitorMute` (`packages/looper_repository/lib/src/looper_repository.dart:5149-5160`) now validates the input identity and requires native admission **before** recording `_monitorMute[input]` and announcing `_monitorChanged(input)`. A refusal leaves remembered intent and the announcement untouched; a stopped engine still records intent as before.
2. The startup replay (`:2655-2674`) admits every remembered mute **before** the enable loop and aborts the start (`stopEngine(); return muteResult;`) on refusal, matching the file's existing replay-failure convention.
3. Monitor restore (`lib/audio_setup/cubit/monitor_cubit.dart:852-872`) and the Session defined-monitor loop (`looper_repository.dart:4188-4211`) split the single mute push into "mute first when muting; unmute last when clearing", and check the result. `MonitorCubit.setMute` (`monitor_cubit.dart:425-439`) gains an `isClosed` guard, an admission check, `addError`, and `rethrow`.

### Boundary ownership is right, and I verified why

`FxChainPersistence._saveMonitor` (`lib/app/fx_chain_persistence.dart:390-409`) reads `_looper.allMonitors()[input]` — repository truth, never the cubit's view. So the repository guard alone closes the persistence leak described in the plan; the cubit's check exists for the *view* and the error report. That is the correct split, and it is why the new "unrelated envelope save stays correct" assertion (`test/audio_setup/cubit/monitor_cubit_test.dart:460-462`) is a real outcome rather than a tautology.

### FFI parity checked against present native source

No native, binding, generated-API, allocation, lock, or thread-ownership change is in this diff. I still read the native entry point for parity:

- `engine_commands.c:3060-3065` rejects `input < 0 || input >= LE_MAX_MONITORED_INPUTS`, and `segno_engine_api.h:24,670` give `LE_MAX_MONITORED_INPUTS == LE_MAX_CHANNELS == 32`. The new Dart bound `[0, kMaxMonitoredInputs)` is therefore FFI-faithful, not invented policy.
- `_monitorMute` is written **only** by `setMonitorMute` (declaration `:1772`; reads `:2656, :4488, :4752`; write `:5157`), so after the guard every key in the replay loop is in range.
- `le_push_cmd` (`engine.c:1303-1313`) returns `LE_ERR_NOT_RUNNING` only when unconfigured, and `a_configured` is written exactly once, to `1` (`engine.c:769`). Since `_intendRunning` is set only after a successful `_engine.start()` (`:2497-2505`), the realistic refusal while running is a **full command ring** (`LE_RING_CAPACITY` is 256, per `test_engine_core.c:1634`), not a device-loss window. This matters: the change cannot silently drop intent during reconnect supervision.
- The ring is fully drained at the top of each process block (`engine_process.c:5816-5819`), so the new ordering is audible only when an audio callback lands between two `le_push` calls — i.e. a bounded one-buffer artifact, not a sustained state. The ordering work is still real, not a no-op.

`stopEngine()` (`:2900-2925`) does not mutate `_monitorMute`, and the replay loop returns immediately after calling it, so there is no concurrent-modification hazard and offline intent genuinely survives a failed start.

## Candidate findings

### F1 — Low/Medium. Refused *clear*-mute aborts restore after the input is already enabled and routed

**Path:** `lib/audio_setup/cubit/monitor_cubit.dart:859-865` (`_applyMonitor`), with the same shape at `packages/looper_repository/lib/src/looper_repository.dart:4195-4201`.

```dart
_repository
  ..setMonitorInputMode(input: input, mode: monitor.mode)
  ..setMonitorOutput(input: input, mask: monitor.outputMask);
if (!monitor.muted) {
  final result = _repository.setMonitorMute(input: input, muted: false);
  if (!result.isOk) return result;      // ← mode + route already pushed
}
```

**Trigger:** a monitor saved with `muted: false` while `setMonitorInputMute` is refused (command ring full during the restore burst — `_restore` applies every monitor synchronously at `:133-136`).

**Impact:** `_applyMonitor` returns non-ok *after* mode and routing were pushed and remembered. `_restore` then throws `StateError` at `:135`, so `emit(MonitorState(inputs: restored))` (`:156`) never runs, `_restored` stays `false`, `_followRepository()` (`:198-203`) never runs, and `_heldReads` accumulate forever — so `_readMonitor` never self-corrects. `load()` is memoized (`:112-116`) and `app.dart:713` calls it as `unawaited(cubit.load())` with the error swallowed into `addError`, so there is no retry and no user-visible notice. Net state: the engine is monitoring the input (enabled, routed, unmuted by native default `a_muted = 0`, `engine.c:220`) while the Monitor surface shows nothing and cannot be recovered without a restart.

The new tests cover only the `muted: true` branch (`monitor_cubit_test.dart:473-503`), where the refusal happens before any other push. The `muted: false` path is exercised only with `refuseMute == false` (`:505-536`).

**Smallest sound correction:** make the clear a no-op when there is nothing to clear, so the common restore cannot fail after the enable:

```dart
if (!monitor.muted && _repository.monitorMuted(input)) {
  final result = _repository.setMonitorMute(input: input, muted: false);
  if (!result.isOk) return result;
}
```

This is sound because, after this PR, `_monitorMute` holds only admitted values and native mute changes only via `setMonitorInputMute` or an engine reset, so `monitorMuted(input) == false` reliably means native is already unmuted. Apply the same guard in the Session loop. Add a regression for "saved `muted: false`, refusing engine" asserting no enable/route mutation.

### F2 — Low. The startup replay is the one path that does not get "destination ready before audible"

**Path:** `packages/looper_repository/lib/src/looper_repository.dart:2655-2674`.

Mutes are admitted first (correct), but the enable loop (`_monitorInputMode.forEach`, `:2666-2670`) still precedes the route loop (`_monitorOutput.forEach`, `:2671-2674`) — and the diff **deleted the comment that documented that order** ("Re-apply per-input live monitors: enable first, then the single chain's routing / mix / effects"), replacing it with a mute-specific comment. So the file now asserts "unmute only after the destination is ready" in two places while the replay contradicts it with no explanation.

**Trigger:** a monitor restored with mode `on`, a non-default output mask, and no remembered mute entry (the common case — `_monitorMute` only gains a key once the user touches mute), with an audio callback landing between the enable push and the output push.

**Impact:** up to one audio buffer of the live input routed to the engine's default mask `0x3` (`engine.c:215`) instead of its saved mask. Pre-existing ordering, not worsened by the diff — but the diff removes its justification and introduces the contrary rule next door.

**Smallest sound correction:** move the `_monitorOutput.forEach` block above `_monitorInputMode.forEach` (route masks are inert while a monitor is disabled) and restore a comment stating the rule once.

### F3 — Low. One ordering rule, now written three times, already inconsistent

`MonitorCubit._applyMonitor` (`monitor_cubit.dart:852-872`), `LooperRepository._applySession`'s defined loop (`looper_repository.dart:4188-4211`), and the `startEngine` replay (`:2655-2674`) each express the mute/enable/route ordering independently, and F2 shows they already disagree. AGENTS.md asks for modular, long-term structure rather than a stopgap. The rule belongs once in the repository — e.g. a private `_applyMonitorIntent({input, mode, mask, muted})` that `applySession` and the replay both call and that `MonitorCubit._applyMonitor` delegates to. Not a defect today; a drift risk this diff creates.

### F4 — Low (test quality). The storage-failure test does not pin the number of error reports

**Path:** `test/audio_setup/cubit/monitor_cubit_test.dart:470` — `errors: () => allOf(isNotEmpty, everyElement(isA<StateError>()))`.

`setMute` now both `addError`s and rethrows (`monitor_cubit.dart:435-438`), while `_persistMonitorAfterFx` independently `addError`s on the `_readMonitor` path (`:260-267`). A loose `isNotEmpty` matcher accepts one report or ten, so a regression that multiplies observation for a single failed save passes. Its sibling at `:502` uses the exact `[isA<StateError>()]` form. Correction: assert the exact list if one report is the contract, or add an explicit count.

### F5 — Low (forward hazard, advisory). `setMute` rethrows and has no production caller

`MonitorCubit.setMute` is invoked only from tests — `grep` over `source/lib` finds no call site (the `setMute` hits in `looper_bloc.dart` / `control_cubit.dart` are `LooperRepository.setMute`, track mute, a different API). `bootstrap.dart:56-59` sets `PlatformDispatcher.instance.onError` to return `false` specifically so unhandled isolate errors tear the process down. The first consumer that uses the conventional `unawaited(cubit.setMute(...))` — #1123 Foot Mixer, per the plan — would turn a refused mute into an appliance restart. It is also inconsistent within the class: `setMode`/`setOutputMask` propagate storage failures without `addError`, and `setVolume` returns quietly on refusal. Not actionable in this PR; worth settling before the consumer lands (keep `addError` as the observation path and return normally, or document that every caller must await).

### F6 — Pre-existing / out of scope, noted because the new test sets the standard

`setMonitorMute` now validates `[0, kMaxMonitoredInputs)`, but its immediate neighbours `setMonitorInputMode` (`:5109-5119`) and `setMonitorOutput` (`:5124-5129`) — called in the same sequences, in all three paths — still have no bound check and still remember out-of-range inputs native refuses, so `allMonitors()` can carry a phantom input. The new test *"invalid monitor mute identity never enters native or remembered rig"* is a good standard the siblings do not meet. Out of this PR's scope.

### Documentation accuracy (in-scope, the doc is part of the diff)

`docs/code-review/monitor-mute-admission/review.md:44-46`: *"Tests prove refusal makes no enable mutation; Monitor restore also makes no route mutation."* That holds only for saved-**muted** monitors. The saved-unmuted refusal path (F1) does mutate enable and route before failing, and is untested. The sentence should be narrowed.

I did verify the one thing about that doc I could: its hash table (`review.md:82-87`) matches `manifest.json`'s `source` hashes for all four files (`40eaf31c…`, `0e1baa9e…`, `f614a722…`, `f97bda11…`). Its reported pass counts and coverage percentages are unverifiable here. I treated it and the plan as claims, not evidence.

## Unverified hypotheses (stated as such, not findings)

- **Ring-overflow reachability during boot restore.** I established the capacity (256, one slot reserved), the per-block drain, and that `_restore` pushes synchronously across all configured monitors. Whether a real appliance boot ever exceeds 255 pending commands between two callbacks is not something static reading can settle. If it never does, F1 and the refusal paths generally are unreachable in practice and the change is purely a correctness tightening.
- I did not find a path where `_intendRunning` is true while native is unconfigured, but I reasoned from `a_configured` having a single write site rather than from exhaustive enumeration of the supervisor's states.

## What I examined and found clean

- **Removed guards:** none lost. `setMonitorMute`'s removed `if (!_intendRunning) return EngineResult.ok;` is behaviourally preserved by the new `if (_intendRunning)` block. `setMute`'s new `isClosed` guard closes a genuine hole: without it, a post-close call reached the engine before `emit` threw.
- **Lifetime / session races:** `_monitorChanges` is a broadcast controller delivering asynchronously (`:1879-1882`), so `_readMonitor` cannot re-enter `setMute`; `setMute`'s own `emit` precedes the announcement and `_readMonitor` computes an identical state (`applied == current`, `:247`) so it neither re-emits nor triggers a second save. `_applyingSessionRevision` is cleared in a `finally` (`:3803-3805`), so a thrown mute refusal leaves the repository usable. `FxChainPersistence._drain` (`:334-386`) retains failed writes in `_dirty` and `_flushOutgoing` (`:453-466`) rethrows, so the "accepted mute survives storage refusal, explicit flush retries" claim is structurally supported.
- **Persistence vs native admission:** consistent — storage derives from `allMonitors()`, which derives from admitted intent only.
- **Shared controller priority / stale gestures:** not applicable yet. No control-binding target for monitor mute exists (`grep` over `source/lib/control` finds none); the shared-holder consumer arrives with #1123.
- **Session reset ordering:** omitted monitors are disabled (`mode: off`) before mute is cleared (`:4176-4179`), as claimed.
- **Test additions are pure additions.** Every test hunk in the diff is `+`-only; no existing assertion was removed or weakened. Pre-existing mock-based `setMute` tests still pass the new admission check because their stubs return `EngineResult.ok` (`monitor_cubit_test.dart:264-273`, `audio_routing_test.dart:132-137`).
- **Test quality is mostly outcome-shaped**, not source-shaped: assertions read engine-visible maps, repository readbacks, the `monitorChanges` stream, and the settings store. The `_RefusingMonitorMuteEngine.monitorSteps` sampling-after-each-accepted-command technique is a legitimate way to observe intermediate engine state, and the `isNotEmpty` guard prevents the invariant loop from passing vacuously. Two specific strengths worth naming: `invalid monitor mute identity…` asserts `muteCalls == 0` against a fake that does **not** itself bound-check, so it proves the repository guard; and `failed startup mute replay…` asserts `engine.monitorInputEnabled` is empty against a fake whose `start`/`stop` do **not** clear that map (`fake_audio_engine.dart:46-73`), so it genuinely proves mute-before-enable rather than trivially passing.
- `pumpEventQueue` is available in the package test (`flutter_test` is imported at `looper_repository_test.dart:7`) and needs no binding.
- No new timer, queue, stream, cache, storage key, dependency, or state owner.
