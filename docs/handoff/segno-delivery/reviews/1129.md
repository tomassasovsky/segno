## Finding 1 — Muting a track rewrites its saved lane FX chains, destroying them when the engine never restored them

**Severity: High (silent, permanent loss of saved user data).**

**Paths**
- `source/lib/app/track_mute.dart:31-46` — every accepted *or refused* mute queues `saveConfirmed(FxAddress(stage: FxStage.loop, …))` for each lane in range.
- `source/lib/app/fx_chain_persistence.dart:732-751` — the `FxStage.loop` writer that this save lands in writes **`settings.saveLaneEffects(...)` first**, then `settings.saveLaneMute(...)`.

**Trigger (verified by code path)**

1. `lane_effects.<ch>.<lane>` is only ever read back into `LooperRepository` by `_tryAutoStartEngine` (`source/lib/app/audio_bootstrap.dart:513-532`; `Grep` for `loadLaneEffects` across `lib/` returns only that site and the session-boot read-back). There is no other restore path.
2. `run_segno.dart:182-223` builds the full UI regardless of the auto-start outcome — the "interface unplugged at boot" state is an expected one (it is why `audioRecoveryConfig` exists). The new lane-mute admission check (`audio_bootstrap.dart:496-512`) adds a further way to reach `started: false` after a *partial* per-track restore.
3. With chains not (fully) restored, `LooperRepository.laneEffects(c, l)` is empty and `laneChainEnabled(c, l)` defaults to `true`.
4. The mixer mute button is not gated on connectivity: `source/lib/looper/view/mixer_column.dart:404-411` dispatches `LooperMuteToggled` unconditionally → `looper_bloc.dart:84-88` → `_setMute` → `applyTrackMute`.
5. `_drain` reaches the write (with the engine stopped `fxRecipesSettled` is true because `_fxPending` is cleared in `stopEngine`, `looper_repository.dart:2926`), and `saveLaneEffects` **overwrites** the key with an encoded empty-enabled envelope (`settings_repository.dart:2028-2029`). Per `clearLaneEffects`' own doc at `settings_repository.dart:2031-2040`, the boot restore reads an empty envelope identically to "no chain", and `audio_bootstrap.dart:516` then `continue`s past it.

**Impact.** One mute tap (or a Clear, which also routes through `_setMute`) permanently erases the persisted per-lane FX chains — entries, chain-enabled flag and `inheritedFrom` provenance — for every lane of that track. Nothing reports it; the mute itself succeeds. Before this PR a mute wrote only `lane_mute.<ch>.<lane>` (`looper_bloc.dart` old `LooperLaneMuteToggled` handler / `_clearAndArm`), so no FX key was touched by a mute.

Corroboration inside the diff itself: `test/control/control_cubit_test.dart` had to add `laneEffects`, `laneChainEnabled` and `laneChainInheritedFrom` stubs to make a *mute* test run — i.e. muting now reads and republishes the whole lane FX envelope.

**Smallest sound correction.** Keep the single per-address queue (that is what fixed TM-1) but make a mute-driven save write only its own key. Add a per-entry flag to `_FxSave`, threaded through `_saveConfirmed`/`_queue`, and **AND** it on supersession so a real FX edit can never be downgraded:

```dart
_dirty[address] = _FxSave(
  settings, _looper.sessionRevision,
  completeOnClose: completeOnClose || (_dirty[address]?.completeOnClose ?? false),
  muteOnly: muteOnly && (_dirty[address]?.muteOnly ?? true),
);
```

`applyTrackMute` passes `muteOnly: true`; `retainConfirmed`/`scheduleSave`/`saveFxOwner` keep the default `false`. In `_writeFxOwner`'s `FxStage.loop` branch, skip `saveLaneEffects` when the entry is mute-only. This also removes the existing wart that `muted` is sampled *before* the lane-effects await (`fx_chain_persistence.dart:733-734`).

(Alternative, larger: restore lane chains into the repository independently of a successful engine start, which fixes the underlying asymmetry rather than this one symptom. That is beyond this slice.)

## Finding 2 — `_muteRecPlay` aborts mid-loop, reporting "refused" after it has already started playback and left part of the rig muted

**Severity: Low (needs a per-channel native mute refusal; self-healing state, inconsistent feedback).**

**Paths** `source/lib/control/cubit/control_cubit.dart:1911-1929` and `1942-1947`.

**Trigger.** In the parked branch, the pre-mute loop (1911-1920) and the resume loop (1922-1925) now `return false` on the first refused `_setTrackMute`. The guard inside `applyTrackMute` is evaluated identically for every channel in a synchronous loop, so the only way to fail on the *second* iteration is a native refusal for one track but not another.

**Impact.** The resume loop can have already unmuted and `play()`-ed earlier members — and the engine unparks the whole loop on the first play, as the comment at 1903-1910 states — yet the function returns before `emit(state.copyWith(parkedResume: const <int>{}))` at 1928. The caller (`_runCommand` → accepted-contact LED, `control_cubit.dart:2578-2579`) therefore reports a refused Rec/Play while audio is running, and `parkedResume` is left unconsumed. The derived `armedTracks` ignores `parkedResume` while unparked (`control_projection.dart:45-51`) and the next `parkAll()` overwrites it, so this heals — the lasting effect is the false "refused" report and a partially muted rig with nothing resumed.

**Smallest sound correction.** Mirror what `_clearAllAccepted` already does for the same class of failure (`control_cubit.dart:2216-2222`): accumulate `var muteAccepted = true;` instead of returning, keep the loops whole, emit as before, and fold `muteAccepted` into the returned bool. That satisfies "a failed prerequisite mute cannot advance a dependent transport action" for the single-track case the tests cover, without leaving the multi-track case half-applied and misreported.

## Verified as sound (checked, no action)

- **`LooperRepository.setLaneMute`** (`looper_repository.dart:5104-5121`): validates identity before any native call or remembered write, and no longer records intent on refusal. Partial whole-track admission is preserved because `setMute` loops `setLaneMute` per lane (`4872-4879`) and `applyTrackMute` persists `laneMuted(c, l)` per lane, so each actual value is stored. `trackMuted` stays "all lanes".
- **Startup replay** (`2640-2650`) follows the established `stopEngine(); return result;` pattern of the surrounding replay steps; iteration is over `_laneMute.entries` and `stopEngine` does not mutate that map, and the function returns immediately.
- **Session apply**: `_clearDestructive` passes `notify: false` (`3467`), so the new `_forgetLaneMutes` notification cannot inject ordinary lane saves into a session transition; ordinary clear/redo paths (`1149`, `3483`, `3696`) notify only for lanes that were actually `true`. `_requireSessionSetting` wrapping of `setLaneMute` (`3958`, `4075`) fails the load rather than reporting a successful restore, and the refused lane leaves no remembered intent.
- **Notify-before-assign ordering** in `_restoreClearedTake` (`3628-3636`) and `_forgetLaneMutes`/`inherited` in `_snapshotAndSettleImages` (`1149-1173`) is safe: `_drain` always suspends at `await settlePending()` before `_writeFxOwner`, so every write reads post-assignment state. The synchronous reentrancy exposure is identical to the pre-existing notification at `1172`.
- **`completeOnClose` lifetime.** I traced every exit of `_drain` (`fx_chain_persistence.dart:359-416`): after a drain ends, `_dirty[address]` is absent, or has `completeOnClose == false`, or is a newer entry — in which case the loop continues rather than ending. So `_close`'s `removeWhere` (`454`) cannot orphan an obligation that nothing awaits, and `close()` cannot drop an admitted controller save or deadlock on the boot barrier (released at `450` before the drains resume).
- **`saveFxOwner` rewrite** (`694-702`) preserves the old `_closed` short-circuit and the old session fence (now `_drain`'s `pending.session` checks), and adds failure retention for flush/retry. All call sites were updated; `looper:` is gone everywhere (`Grep` over `lib/`, `test/`, `packages/`).
- **`SettingsRepository`** (`2006-2020`): `saveLaneMute` goes through the existing `_serialize` chain with `_writeBoolScalar` read-back; `loadLaneMute` awaits `_serializedWrite`. No `_serialize` body calls either, so no self-deadlock. Errors are swallowed in the chain tail, so a failed write does not wedge later writes.
- **Session boot image**: `laneMutes` covers all 8×`kMaxLanes` slots (`kMaxLanes == 8`, `LE_MAX_LANES`), so omitted slots are reset; the image stays immutable across `retrySessionBoot`.
- **Single ownership**: `Grep` for `.setMute(`/`.setLaneMute(` across `lib/` returns only `track_mute.dart` and the bootstrap restore. No production mute write bypasses the shared operation, and the bootstrap restore correctly does not re-persist.
- **Error surfacing**: `addError` only logs (`bootstrap.dart:10-29`); it cannot escalate a routine session-transition refusal into a crash.

## Behaviour changes worth a conscious decision (not defects)

- A persisted lane mute that native refuses at boot now aborts auto-start entirely (`audio_bootstrap.dart:499-511`, shared `admitted` helper, `recoveryConfig: null`). Consistent with every other saved setting in that function and with the plan, but it converts an ignorable refusal into "no audio at all". I cannot inspect `le_engine_set_lane_mute` (native omitted), so I cannot bound how reachable a refusal for an in-range, active lane is.
- A Clear or mapped Clear now reports failure when only the dependent unmute was refused (`control_cubit.dart:2227`, `2245`, `2613-2616`), suppressing the pedal accepted-contact LED for a clear that did happen.
- `_clearAndArm`'s new `sessionTransitionActive` early return (`looper_bloc.dart:932`) is redundant in production: its single caller already checks `_takeLocked()` (`looper_bloc.dart:61`), which `AppRuntime` wires to `takeLocked`, itself including `fxPersistence.sessionTransitionActive` (`app_runtime.dart:61`, `132-133`). It is load-bearing only in unit tests, where `takeLocked` defaults to `_neverLocked`. Duplicated invariant, silent swallow.
- Session load now performs 64 extra serialized `setBool` + read-back round-trips. Bounded, and small relative to the 64 lane-effects writes already there.
- `applyTrackMute` hardcodes `channel >= 8` rather than referencing `LE_MAX_TRACKS`; it matches local convention in `LooperRepository` (e.g. `setLaneCount`, `5104`), so the duplication is pre-existing in kind.

## Test quality

The new suite is mostly outcome-based rather than source-shaped: `test/looper/bloc/track_mute_persistence_test.dart` asserts storage read-back via `settings.loadLaneMute` and performs real cold boots through `tryAutoStartEngine` against a fresh engine, checking `freshEngine.laneMute[(0, 0)]`; partial admission asserts `[true, false, true]` in both the remembered intent and storage; the failure cases assert `store.values[...]` and that `flush()`/`close()` reject. `settings_repository_test.dart`'s ordering test genuinely pins the read behind the two writes.

Gaps I would ask to close:

- **No case covers Finding 1.** Every test in the `shared track mute operation` group calls `startEngine` in `setUp`, so the "chains never restored" state is never reached. A test that saves `lane_effects.0.0`, boots with a refusing/absent engine, mutes, and then asserts `loadLaneEffects(0, 0)` is unchanged would have caught it.
- **No multi-track case for Finding 2.** `'refused parked unmute cannot play or consume resume membership'` is a real assertion (entering mute mode latches `parkedResume = {0}` at `control_cubit.dart:1728-1738`, so the unchanged-`{0}` check can fail), but it only exercises one track, which is exactly the case where mid-loop abort and accumulate-and-continue agree.
- `control_cubit_test.dart` and `looper_bloc_test.dart` stub `setMute`/`setLaneMute` to mutate a local `laneMutes` map that is keyed on lane 0 for whole-track mutes, so they cannot observe whole-track multi-lane behaviour. Acceptable, since the repository suite owns that, but the assertions in those two files are about calls, not outcomes.
- `'a failed controller save leaves no sticky disposal obligation'` asserts the mute is *not* written at close and does not assert that the caller was told; the mute is silently non-durable on that path (acceptable per the documented disposal posture, but the test name reads as if nothing was lost).
