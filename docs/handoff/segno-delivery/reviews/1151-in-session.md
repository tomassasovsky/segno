# Findings

## 1. Medium: the restore-failed gate misses the FX page path, so the clobber it targets is still reachable
- Path: `lib/looper/cubit/fx_cubit.dart` `_replaceChain` (:109-112), `_editChain` -> `_persistence.saveConfirmed` (:177), `setGroupEnabled` (:371-399), param write (:452-485) with `scheduleSave`. All have an `FxStage.input` branch that writes the repository directly and persists via `FxChainPersistence._saveMonitor` (`lib/app/fx_chain_persistence.dart:464-482`). `fx_cubit.dart` has no reference to `MonitorCubit` or `restoreFailed`; `_currentChain(FxStage.input)` (:80-86) just reads `repository.monitorEffects`.
- Trigger: restore fails (`monitor_cubit.dart:146-150`, e.g. "saved monitor FX was refused", or the `sessionTransitionActive` branch at :128), the user then appends, reorders, toggles or tweaks an input-stage effect on the FX page.
- Impact: `_saveMonitor` writes the repository's mode, output mask and mute (defaults) and the new chain over the saved keys. This is the same silent loss the PR says it prevents ("monitor mode, routing and FX edits are refused while restoreFailed"). The PR text and the `_editable` doc comment overstate coverage. Only MonitorCubit-originated edits are gated.
- Smallest fix: make the guard live where the write happens. Either have `_saveMonitor` / `FxChainPersistence` refuse input-stage saves while a flag set by MonitorCubit (`restoreFailed`) is up, or have `FxCubit._currentChain` return null for `FxStage.input` while it is. Add a test through FxCubit.
- Not traced: `lib/control/binding/*` writers call the repository directly for input chains; their callers' persistence (the "skip the persist" comment at `fx_binding_resolver.dart:93`) was not followed.

## 2. Low: the write-back can abort `loadMixSettings` after a successful read
- `settings_repository.dart:1602-1605`: `await _serialize(...)` propagates any store failure or a re-read FormatException to the caller. `audio_bootstrap.dart:230` catches only FormatException (:209), so a storage write error on a legacy install escapes `tryAutoStartEngine` and `run_segno`'s unguarded await, where a read-only call previously succeeded.
- Impact: boot failure on a failing store for installs that carry a gain in (1, 2]; otherwise none.
- Smallest fix: make the write-back best-effort (try/catch, log, still return `saved`); the repair is idempotent and retried on the next load.

# Verified correct (no finding)
- Clamp (`settings_repository.dart:1499-1507`): `legacy` requires finite and 1 < g <= 2. Other values (negative, >2, infinite, key outside 0..31) still reach `_validMonitorLevels` and throw before any write. The legacy flag is only consumed after validation passes. A blob mixing one legacy and one invalid gain still fails closed with bytes unchanged.
- Write-back serialization: the first read follows `await _serializedWrite` (:1600-1601) and is a snapshot only; the write-back re-reads inside `_serialize` (:1604), so a write queued in between is not lost. Two concurrent loads both rewrite the same clamped value (idempotent). The returned `saved` is the clamped first read, consistent with storage after the repair.
- Other `_readMixSettings` callers: `loadMonitorVolume` (:1177-1178) returns 1.0 without writing; storage stays legacy until the next load or any mix write. `saveMonitorVolume` (:1183-1191) and `replaceMixSettings` (:1658-1682) read the clamped value and rewrite the whole blob, which repairs it incidentally. The reads are consistent; the only difference is that the repair is deferred. The bootstrap pre-read at `audio_bootstrap.dart:230` runs before any of these and before MonitorCubit restore, so in the normal boot order the repair precedes `_restoreInput`'s `loadMonitorVolume`.
- Write-back keeps unity entries as `1.0` (`encoded`, :1527-1529), while `saveMonitorVolume` removes them. `replaceMixSettings` also persists unity entries from the coordinator candidate, so this is not a new inconsistency.
- Migration clamp (`monitor_migration.dart:173-178`): removes the ArgumentError path from `saveMonitorVolume` for legacy lane gains. It also clamps values above 2, where the reader would fail closed; acceptable for a conversion.
- Gate coverage in MonitorCubit: gated are `setMode` (:459), `setOutputMask` (:468), `addEffect`, `appendEffects`, `insertPlugin`, `relinkPlugin`, `removeEffect`, `moveEffect`, `setEffectPlacement`, `setEffectType`, `setEffectParam`, `setPluginParam`, `setEffectChannels`, `setEffectEnabled`, `setChainEnabled`, and `_pushEffects` itself (:878). That last gate covers `setEffects`, `setEffectsConfirmed` (returns false on notReady) and `appendEffectsConfirmed`. `setMute` goes through `saveMonitorMuteConfirmed`, which is `muteOnly` and writes only the mute key (`fx_chain_persistence.dart:293-300, 421-430`). `openPluginEditor` / `closePluginEditor` (:842-864) are ungated but only emit state and persist nothing.
- `setVolume` (:476) is not a "own key only" write: it goes through the coordinator to `replaceMixSettings`, which rewrites the whole mix blob from the repository snapshot. That is correct after boot, because `audio_bootstrap.dart:441` pushes `savedMix.monitorLevels` into the repository before MonitorCubit restore. The doc comment (:116-117) is imprecise, not wrong in effect.
- Retry: `load()` leaves `restoreFailed` true while retrying (edits stay refused), and the success emit at :248 clears it. `projectFromRepository` (:447) also clears it. `withInput` preserves the flag. The existing test at `monitor_cubit_test.dart:488-492` covers the Retry transition.

# Optional notes
- Residual risk, restore in flight: `restoreFailed` is false from construction until a failure (`app.dart:741` fires `load()` unawaited). An edit during the first restore passes the gate: `setMode` persists repository defaults for the other keys and chain while `_restoreInput` may have read before or after that write. The window is short (startup) and predates this PR. Gating on `_restored` as well would close it, but needs test setups that call `load()` or `projectFromRepository`.
- `_foldInputToSingleChain` still runs `saveMonitorVolume`, which reads the blob; a truly malformed blob (e.g. 2.5) still throws FormatException from `runMonitorMigration` (`run_segno.dart:172`, unguarded, before bootstrap's handler). Only unmigrated installs with a bad blob.
- Tests: the legacy test uses `loaded.monitorLevels[1] ?? 1`, which does not pin whether the unity entry is stored; it does not assert "once" (no second-load write check). The gate test never exercises FxCubit (finding 1), a post-Retry edit, or that volume and mute still write while failed.

# Verdict
Settings clamp, write-back ordering and migration clamp are correct as traced. The cubit gate is incomplete: FxCubit input-stage edits still persist defaults over saved monitor settings after a failed restore (finding 1). Request changes on finding 1 or narrow the PR claim; finding 2 is a small hardening.
