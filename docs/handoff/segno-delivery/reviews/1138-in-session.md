## Traced behaviors (all confirmed sound)

1. Exact rollback. fade_settings.dart:`_persist` reads the exact prior bytes/absence, writes via `saveFadeDurations` (= verified `restoreFadeDurationsCheckpoint`, settings_repository.dart ~240-262), and on any throw (write-then-throw, mismatching readback) records `_repair = (bytes: checkpoint)` and attempts the exact restore. The record wrapper distinguishes owed removal from no debt. A failed repair keeps the debt; `confirmed` (throws when `needsRecovery`), `_edit` and `flush` all refuse until `recover()` succeeds. `_confirmed` changes only after verified success. A failing checkpoint read happens before any write, so no debt arises.
2. Tail never strands. `_enqueue` and `runExclusive` both swallow errors in `_tail`, so a failed edit/scope cannot block later work.
3. Exclusion and drain. `runExclusive` increments `_exclusive` synchronously, runs the action synchronously via `Future.sync`, so the inner `_mix.runExclusive` reservation stays immediate (the app_runtime_test asserts a Mix edit is superseded at once). Later `_edit`/`recover` are refused while `_exclusive != 0`; edits admitted earlier are in `prior`. The early-other-owner error (Mix `_exclusive` throws `MixSettingsRecoveryException` before the callback that awaits `admittedEdits`) is handled by `.whenComplete(() => prior)`, which delays both the result and the `_exclusive--`/`_tail` release until admitted edits finish. No self-wait: `installSession` never enqueues; no code inside the scope calls `flush`/`recover`/`close`. Lock order fade -> mix -> tempo -> playback -> record -> timing has no inverse use.
4. Close. `close()` sets `_closing`, then awaits `_tail`, which includes admitted edits, recover, load, and any scope started before close; `_results.close()` runs only after. `_edit`, `recover`, `load`, `runExclusive` refuse after `_closing`. `installSession`'s `_results.add` happens inside a scope already in `_tail`. AppRuntime._close orders `fade.close` after session and `fxPersistence.flush`, with each disposer failure isolated.
5. Session load. The incoming vector is validated twice before any side effect (`Session.fromJson` strict decode; `FadeDurations(...)` at session_cubit.dart:239, before disarm/mix write/applySession). It is retained in `_pendingLoadedFade` right after `applySession` succeeds, before `persistLoadedSession`. Order is FX boot -> `installFade` -> bindings -> `completeSessionBoot`. `retryLoadedSession` reuses the retained vector inside a new exclusive scope after `retrySessionBoot`. `installSession` repairs any outstanding checkpoint first and then writes the incoming vector, so ordinary repair debt never restores outgoing settings over an accepted Session. Ordinary `recover()` is refused while `fxPersistence.sessionTransitionActive` (`_sessionLoadRequested` stays true until `completeSessionBoot`), and ordinary edits are refused by `takeLocked`, which includes the same predicate. Repeated install failure keeps the vector and the existing launch/binding block.
6. Startup interleavings. `load()` is a no-op once `_loaded`, so a load queued behind a successful Session replacement cannot overwrite the incoming vector, and one queued behind a canceled Session still restores local data. A failed load keeps `needsRecovery`; Retry re-reads. Power Retry runs `session.retryLoadedSession()` first, then `fade.recover()`; notice dismissal uses `results` null events and the recoveries map. Subscription is installed before `start()`.
7. Equality/hash. `FadeDurations` == and hashCode cover both default and the map (unordered hash); `Session` == and hashCode include `defaultFadeDurationMs` and the override map; the new tests assert Default-vs-Custom membership, key order independence and hash equality, so round-trip equality is not the only evidence. Codecs reject 0/499/501/30001, doubles, strings, channels 8/-1/"00", missing fields, and version 9.
8. Native oracle (by reading). At 8 kHz, 4 s travel is 32000 frames; 8000 frames gives 1-0.25=.75; the edit emits no command; another 8000 frames gives .5 with `fullTravelSeconds` still 4. The reversing toggle at 8 s gives .5+8000/(8000*8)=.625, target 1, seconds 8. `le_fade_tick` returns the pre-advance amount and output peaks are per-callback maxima stored at block end (engine_process.c ~6321), so a one-frame pump gives `.5*amount` as asserted, provided unity master/pan path (not independently verifiable here). Tolerance is one frame (1/32000). Mixer volume, undoDepth and exported PCM (.5) are asserted unchanged. The test is skipped without SEGNO_ENGINE_LIB; I did not observe it run.

## Preexisting / design consequences (not blocking)
- A malformed present `looper.fade_durations` record cannot be fixed by Retry (it re-reads the same bytes). Meanwhile `confirmed` makes Session save fail and `fade.flush()` makes power-off flush fail. Only a successful Session load (which overwrites the record via `installSession`) or manual removal clears it. This matches the accepted "malformed present data fails" boundary and the existing record-timing owner (a malformed value there also lands in recoveryRequired and blocks flush), so I do not call it a defect; the owner may want to know it can block power-off on the appliance.
- The 500/30000/500 and 0-7 rules are written three times (FadeDurations, Session._fadeDuration/_fadeChannel, and the tests). Intentional because Session must not depend on SettingsRepository; drift risk only.

## Unconfirmed hypothesis
- `_read()` (fade_settings.dart) does not consult `_repair`. If a load were ever to run while an install-failure repair debt exists and `_loaded` is false, `_confirmed` could come from the unconfirmed incoming bytes and the later `recover()` would restore the old bytes without re-reading. I could not construct a reachable schedule: edits need `_loaded`, `start()` is called once in initState, and a Session scope drains an admitted load first. Not worth code unless startup load is later made re-entrant.
